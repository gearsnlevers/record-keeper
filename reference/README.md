# Reference implementations and test generators

This folder is how the kit is checked against something other than itself. It is not part of the protocol, it is not delivered to a repository that uses the kit (it is not in `install.json`), and `npm test` does not run it, except that `test/manifest.test.mjs` runs `verify_manifest.py` when `python3` is there. The library (`record-keeper.mjs`) needs none of it; whoever changes a rule or a fixture does.

## What is here

- **A second implementation of each page.** Python (`*_ref.py`, `g1.py`) and, for two pages, Node (`g1.mjs`, `validate_ref2.mjs`). Each is written from the page and shares no code with `record-keeper.mjs`. The page decides: when a reference and the library disagree, one of them is wrong about the page, and the page is read again.
- **Builders** (`build_*.py`). A builder writes a fixture: the cases are written by hand together with the answer the author expects, the reference computes the answer, and the builder stops when the two differ. So a case shows what it was written to show, and a fixture cannot drift from the reference without someone seeing it.
- **Fuzz** (`fuzz/`). Random inputs go through a reference and through the library, and a comparer lists every difference. A run that finds no difference proves little until the same run has been shown to find one, for example against the library as it was before a fix.
- **Mutation scripts** (`fuzz/mutate_*.py`, `mutate_g1.py`). One line of the library at a time is changed in a copy, and the tests must fail. A mutant that survives is a missing test, or it is equivalent to the original and is said to be.

## The rules for changing any of it

1. **The page first.** A rule changes in its page, then in the reference, then in the library. A reference is never edited to make a fixture or the library pass without the page being read.
2. **Never edit a generated fixture by hand.** Change the builder and rebuild. `check-fixtures.sh` rebuilds all of them and compares them with the committed files byte for byte; a pull request that changes a builder or a fixture should leave it printing `same` for every line.
3. **The generation g1 is frozen once record 0001 is accepted.** `build_vectors.py` and `g1.py` then change only to add vectors that move no existing answer.
4. **The kit names no deployment.** A script that wants a corpus of real records takes the folders as arguments (`g1_mutants.py`, `run_vectors.mjs`) and does not know whose they are.

## Running it

Needs Python 3.9 or later, git and Node 22 or later. `fuzz/config_oracle.py` also needs PyYAML and Ruby, and for its third reader a folder where `npm install yaml` was run, named in `YAML_DIR`, because it asks three real YAML readers what a settings file means.

```sh
reference/check-fixtures.sh                       # rebuild every fixture and compare; a few minutes; CI runs it too

# a fixture builder writes to the path it is given; build into a scratch folder, not into test/
python3 reference/build_change_cases.py /tmp/cases.json && cmp /tmp/cases.json test/fixtures/change/cases.json

# the second implementation of g1 against the vectors, and against g1.py on some folders of records
node reference/run_vectors.mjs test/vectors/g1 [folder-of-records ...]
node reference/run_cases.mjs test/fixtures/validate reference/validate_ref2.mjs

# a differential fuzz of check-pr: 4000 random pull requests, 4 workers, seed 7
reference/fuzz/change_batch.sh /tmp/change-fuzz 4000 7 4 && cat /tmp/change-fuzz/result.txt

# mutation testing of the lines of record-keeper.mjs that differ from a commit
python3 reference/fuzz/mutate_diff.py . 4 <base commit>
```

`check_ref.py` holds the files that the check guards (`WORKFLOW_FILES`, `CODE_FILES`, [the files of the check](../docs/protected-files.md)) written out and not built, as a second implementation should; `fuzz/change_fuzz.py` puts files at all of those paths, and `fuzz/change_compare.mjs` prints how many scenarios had a workflow or code act at each path, which shows that the guard is exercised everywhere and not only that the two programs agree. `verify_manifest.py` is run by the release workflow as well as by the tests, so it is the one file of this folder that a release job needs.

`fuzz/update_batch.sh <dir> <count> <seed> <workers>` is the differential fuzz of the core of the updater (`updater.mjs`: `plan`). `update_fuzz.py` does not draw its inputs blindly: it asks the reference which release the options choose and builds the manifest of that release, right or damaged in one of about sixty ways, a pinned release with a manifest of its own, the digests of what was downloaded and a working tree in every state, so that the plan reaches the branches that a blind input stops in front of. `result.txt` in the folder says how many inputs were compared and how many answers differ, how many inputs ended in each answer and reached each part of a plan, which branch no input reached (the run fails when there is one), and, from the coverage that V8 records of the Node run (`update_coverage.mjs`), which lines of the core never ran: today the two lines that rethrow an error that is not a refusal. A run that finds no difference proves little, so it was tried on the program with a line changed (fourteen changes, thirteen of them found by the first draw; the fourteenth, a limit of three removals, was found only after the generator was made to remove more files).

`fuzz/setup_batch.sh <dir> <count> <seed> <workers>` is the same for the core of the setup check (`setup-check.mjs`: `decide`, `parseCodeowners` with `matches` and `ownersOf`, `parseUtc`). `setup_fuzz.py` starts from a repository in which nothing is wrong and damages it at random in the places the page lists, with the edges of every limit (48 hours and five minutes to the second, 30 owners, 8 paths) drawn more often than chance would; it also draws CODEOWNERS files from the parts of the six paths that the check asks about, with patterns that are not read, and times that are almost times. The summary counts every branch (every finding, every topic that is checked and every topic that is not, every state of every part of the input) and the run fails when one is not reached; `setup_coverage.mjs` says which lines of the core never ran. A run of 40,000 inputs (seed 11, four workers, about eight seconds) compared 40,000 answers, found 0 differences, reached every branch and ran every line of the core. It was tried on the program with a line changed (fifteen changes, thirteen found by the first 4,000 inputs; the two that were not are equivalent: `approvals <= 1` for `approvals === 1`, because the settings reader allows no `approvals` below 1, and a memo that is switched off, which changes the time and not the answer).

`fuzz/agent_batch.sh <dir> <count> <seed> <workers>` is the differential fuzz of the block of `AGENTS.md` (`updater.mjs`: `readBlock`, `blockOf`, `spliceBlock` and `blockChanged`, [the files that agents read](../docs/agent-files.md)). Each scenario is a file and a block and writes three lines: where the block is, what the file becomes when the block is put into it, and whether what agents read changed between the file and another one made from it by one of about twenty edits (or by chance). `agent_fuzz.py` makes the files from lines of text, markers, markers that are damaged in a dozen ways, fences of every shape, prose that holds the text of a marker, three kinds of line end, bytes that are not UTF-8 and zero bytes, around zero, one or two blocks or half of one, so that every branch is reached often. The reference asserts on every answer what the updater counts on and the Node run asserts it again on its own answers: the block that was put in is found and is the block, a second splice changes nothing, **not a byte before the begin marker or after the end marker changes** (and an append only adds to the end), and the comparison is symmetric. A run of 50,000 scenarios (148,497 lines, seed 21, four workers) found 0 differences and 0 broken invariants, reached every branch that `agent_summary.py` lists, and ran every line of the block functions (`agent_coverage.mjs`). `update_fuzz.py` and `setup_fuzz.py` draw the block, the skill, `CLAUDE.md` and the states of `AGENTS.md` too, so that the plan of the updater and the decision of the setup check reach their branches for the new files; their runs of 40,000 inputs (seeds 31 and 41) found 0 differences and reached every branch, and `update_coverage.mjs` leaves out the block functions, which `agent_coverage.mjs` covers. `change_fuzz.py` edits the skill and `AGENTS.md` in a dozen ways (inside the block, outside it, the markers, a fence, a link, a folder, a mode, line ends) and `change_compare.mjs` counts the acts of the kind `instructions` at each of the two paths: 1,500 scenarios, 0 differences, 273 acts of the kind.

`fuzz/mutate_change.py` mutates every line of the part of the library that checks a change, `fuzz/mutate_pr.py` every line of `check-pull-request.mjs` (or of another program: `MUT_FILE`, `MUT_TESTS` and `MUT_LINES` name it, its tests and the lines to mutate, as `a-b` pairs; `MUT_STRIDE=n` runs every nth mutant (`MUT_OFFSET=k` from the kth), for a program whose tests take long, as those of `updater.mjs` do; `MUT_CONFIRM=1` runs each mutant that was killed once more, so that a kill that came from a test that failed for a reason of the machine is not counted; `AUDIT_RUN_STRIDE=8` makes the tests of `run-audit.mjs` run a sample of their cases, for a quick first pass) and `mutate_pr2.py` only the lines that differ from a commit, and `fuzz/mutate_note_case.py` is an example of a hand-written list of mutants for one change. The batch scripts and the other fuzz scripts say how they are called in their first lines.

`fuzz/length_batch.sh <dir> <count> <seed>` is the differential fuzz of the length that V-10 counts: the record without its `Known deviations` and `Errata` sections. `length_fuzz.py` draws the length outside the sections around the cap (most of them 58 to 62) and writes records of three kinds: pairs (a record, and the same record with sections appended after the empty line that g1 asks for, or one put before `Alternatives considered`), records whose sections hold lines that end a section (a heading of level 1 or 2, with up to three spaces in front, bare, with a tab) or that only look like one, and records that g1 refuses. Reference 1 answers, and the program checks on every pair the invariant of the page: with the sections or without them the count is the same, so whether V-10 is reported is. Reference 2 and the library are then compared with reference 1 (`validate_compare_ref2.mjs`, `validate_compare.mjs`). Three runs of 6,000 draws (seeds 7, 11 and 23) compared 28,876 folders, 10,876 of them in pairs (5,101 pairs over the cap): 0 differences between the three implementations and 0 pairs that changed the count. Two runs of `validate_fuzz.py` on the fixtures as they are now (3,000 folders each, seeds 5 and 9) found 0 differences. The first run of 9,597 folders found each of the 28 changes that were tried on the library and on reference 2 (the breaks of `mutate_length.py`).

`fuzz/mutate_length.py` is the mutation test of that count in the three implementations, with the breaks that the page names (the sections counted again, no rule for the empty line after a final line feed, an off by one on the empty line before a section) and the places where a section ends. It has 40 changes: 23 of the library and of the canonical form that shares the cut with it, 2 of the check of a change (the waiver of V-10 for an erratum is kept: a change that asks V-10 of an erratum is killed), 8 of reference 1 (killed by `build_cases.py`, which stops when a case is not what it was written to show) and 7 of reference 2 (killed by `run_cases.mjs`). 39 are killed; the one that survives is equivalent: V-10 asked of a deviation note, which changes no line that V-10 counts, so there is nothing to bring. `mutate_diff.py` on the lines of `record-keeper.mjs` that differ from the commit before has 17 mutants, all killed by the tests of the format, of g1 and of the records.

CI runs `check-fixtures.sh` in the workflow `Reference` (`.github/workflows/reference.yml`), on a pull request or a push to `main` that changes `reference/`, `test/fixtures/` or `test/vectors/`. It is not a required check: it has a path filter, which is only safe for a check that nothing waits for.

The builders delete the folder they are given (`build_vectors.py`, `build_cases.py`), so they are never pointed at a folder under `test/` that holds a hand-written `README.md`.
